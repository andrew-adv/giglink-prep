## What changed

- Mongoose `LearnerProgress` stores one document per anonymous learner: the exact six-file workspace, completion IDs, attempts, selected lesson, version 2, revision, and server timestamps. The token is generated by browser cryptography (32 random bytes), stored only on the device, and sent in an Authorization header. Only its SHA-256 digest is used as the database `_id`.
- `GET /api/progress` and `PUT /api/progress` deliberately avoid the original prompt's `:learnerId` URL. A bearer credential in a URL could appear in routine access logs. No token, database URI, host, driver exception or submitted code is logged or exposed in public errors. The UI and README explain that anyone holding the token may access/replace that saved work.
- The shared public contract rejects unknown fields, operators, missing/extra code files, invalid schema/lesson/completion values, and invalid attempts/revisions. Six file strings are limited to 50,000 characters each and the encoded body to 512 KiB. Timestamp and database identifier fields are never accepted from the browser. No submitted code is executed by Express.
- Creation relies on MongoDB's unique `_id`; updates atomically match the expected revision and increment it. Duplicate creation or stale revisions return 409 with the current progress snapshot. This follows MongoDB's [single-document conditional update behavior](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/).
- Database buffering is disabled. Missing configuration starts the API with local-only saving; failed initial connections retry in 30 seconds. Connection/operation timeouts are bounded. `/api/health` remains 200 for the running API and reports `connected`, `unavailable`, or `not-configured`. Save/read returns 503 without a usable database. Shutdown closes HTTP and MongoDB, with a 10-second deadline. The database is explicitly `giglink_prep` even if a URI names another database.
- Local workspace v2 and P1 migration/backup are unchanged. The new learner token and sync baseline/recovery use separate keys; the theme key is unchanged. Local work renders first, before a background GET. Changed content is saved remotely after a 900 ms debounce. There is no PUT for an unchanged project, theme change, or guide interaction.
- Reconciliation compares actual workspace content and last acknowledged server revision. Newer local/offline edits cannot be silently replaced by a delayed or stale server response. Divergent, missing, or older server copies pause for a choice. Both copies are retained before replacement, with JSON download buttons. Only the most recent conflict pair is retained.
- Offline/failed/ambiguous writes show waiting, retain local work, and retry after 30 seconds, on an online event, or on demand. Recovery reads before writing again. Server-saved status requires confirmation. Edits made during a PUT receive a separate follow-up save. Unsaved memory-only edits cannot become a remotely acknowledged baseline.
- Narrow integration changes key the existing coding lab by remote workspace replacement and require a choice when the editor is already open. Thus pending editor edits cannot be preempted by automatic hydration, and an open editor reloads explicitly chosen files instead of writing stale files back over them. Sandpack execution, grading contracts, guides, CTO answers, simulations, and themes are unchanged.


The restricted connection attempt failed; the approved network-capable rerun **passed**. Through real HTTP routes and the actual Mongoose model it verified:

1. Creation, readback and update of six-file progress in `giglink_prep`.
2. A different random learner credential cannot read that work.
3. Two writes at the same revision produce one success and one 409.
4. Closing/reopening the HTTP API and MongoDB connection retains the exact saved workspace and revision.
5. The document is present in MongoDB after reconnection; the script deletes only its own temporary random record afterward.

This is a real database integration check, not a browser test or proof of a full Node process restart. The procedure below covers the latter and Atlas inspection. The script deliberately prints only pass/fail descriptions, not credentials or learner code.

## Manual setup and QA

1. Follow README setup: `npm ci`; preserve existing private env files; put your own Atlas URI only in `server/.env`; use a separate Prep database user with read/write to `giglink_prep` and appropriate network access. Set the public frontend API URL and exact `CLIENT_ORIGIN`. Run `npm run dev`. Health must show `database: "connected"` for server saving. Without configuration, verify local learning continues and health says `not-configured`.
2. Open the app with an existing P1/P2 browser profile. Confirm all six code files, completion, attempts, selected lesson, theme and guides. Edit a fictional marker such as `// p3-restart-check` into `gig.js`; wait for **Saved on this device and server**. Do not clear storage or expose the token. Confirm a Network GET/PUT response contains your workspace and revision; do not copy Authorization headers into reports.
3. In Atlas Data Explorer open `giglink_prep.learnerprogresses`, sort by `updatedAt` descending, and expand your recent document. Check the marker, six code strings, current lesson, completed IDs, attempt counts, revision, and timestamps. `_id` is a digest, not the bearer token.
4. Stop the API's entire Node process (Ctrl+C when running separately with `npm run dev:server`). Keep the frontend running with `npm run dev:client`. Refresh; device code must still load immediately. Edit another fictional marker while the API is stopped. Expect **Saved on this device / Waiting to sync**, never a new cloud-saved claim. Refresh again to verify local recovery.
5. Restart the API with `npm run dev:server`. Wait for database connection, then **Try sync now** or the next retry. If the server has not changed, offline edits should sync; otherwise the UI must ask which copy to keep. Confirm the new revision and marker in Atlas. Stop/restart the full API process again without editing. Refresh the page and inspect the initial progress GET response to prove the saved document survives the process restart independently of browser memory.
6. With two tabs initially at the same confirmed revision, save different fictional edits in tab A and then tab B. Tab B must show a conflict, keeping its current code. Download both copies; choose **Keep device version** and wait for server confirmation. Repeat and choose **Load server version**; confirm the already-open editor uses that chosen code and recovery downloads include both previous copies. This is explicit conflict resolution, not automatic cross-tab merging.
7. After initial reconciliation, clear the Network request list. Switch Dark/Light/System and open/advance/replay/close a guide. There should be **no progress PUT**. Change actual learner code or start an attempt; expect one debounced save. Refresh and confirm code and theme restore independently.
8. Test a failed database/API connection and recovery without discarding work. Keep this tab open if browser storage is full/blocked; copy/download code. A failed local write must never silently replace the workspace or count as a durable sync baseline.
9. Verify at 320/390 px: save banner, conflict actions/downloads, theme/navigation, editor and guides fit without page overflow. Check keyboard focus. Run wrong and correct learner code in real Sandpack; complete `/replay`; open `/questions`. These browser-only checks remain unverified because of the earlier denied browser access.

## Limits

There is no signup/recovery service, cross-device account, import flow, automatic merge, live subscription to remote edits, or complete history. Storage/token deletion loses browser access to that anonymous save. Recovery retains only the latest conflict pair, and storage failures require manual downloads/copying. Server progress is validated storage, not secure re-grading. No P4 deployment, provider auth, personal profile, analytics, payment service or real uploads were added.
